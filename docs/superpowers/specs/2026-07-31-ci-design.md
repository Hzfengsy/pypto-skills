# Continuous Integration Design

## Context

The repository has 93 standard-library `unittest` cases covering the three
portable skills, their shared GitHub workflow library, and the shell helpers.
Those tests currently run only when a contributor invokes them locally. One
positive Bubblewrap test also skips when the host cannot start the isolation
sandbox, which would allow a CI run to appear healthy without exercising the
most important security boundary.

## Goals

- Run the complete discovered test suite for every pull request and every push
  to `main`.
- Keep the test harness compatible with the documented Python 3.10+ baseline.
- Treat a non-operational Bubblewrap sandbox as a CI failure.
- Check Python style, Python types, and shell syntax with reproducible tool
  versions.
- Give the workflow only read access to repository contents and keep checkout
  credentials out of the test environment.

The workflow will not publish skills, synchronize consumer repositories, run
tests on non-Linux operating systems, or require local developers to have
Bubblewrap when they are not running in CI.

## Chosen Approach

Use one GitHub Actions workflow with two independent jobs:

1. `quality` runs the static checks once on Python 3.14.
2. `tests` runs the full suite as a Python 3.10 and Python 3.14 matrix.

This keeps failures attributable to either static quality or runtime behavior,
while the matrix protects both the minimum supported interpreter and the
current stable interpreter. A single job would be slightly faster but would
hide compatibility gaps. A container-based job was rejected because nested
Bubblewrap isolation introduces extra privilege and user-namespace
configuration that is unnecessary on a GitHub-hosted virtual machine.

## Workflow

Create `.github/workflows/ci.yml` with these triggers:

- `pull_request`
- pushes to `main`
- `workflow_dispatch`

Use the `ubuntu-22.04` runner image, workflow-level `contents: read`
permission, and concurrency cancellation for superseded runs from the same
pull request or branch. Ubuntu 22.04 avoids the additional unprivileged
user-namespace mediation introduced in Ubuntu 24.04 while remaining a
GitHub-hosted image. Pin `actions/checkout` 6.0.2 and
`actions/setup-python` 6.2.0 to full commit IDs and keep those release versions
in comments. Checkout must use `persist-credentials: false`.

The `quality` job will:

1. Check out the repository.
2. Install the pinned CI-only Python tools.
3. Run `ruff check`, `ruff format --check`, and `pyright`.
4. Run `bash -n` for every tracked `.sh` file.

The `tests` job will:

1. Check out the repository without persisted credentials.
2. Install the selected Python matrix version.
3. Install the operating-system `bubblewrap` package.
4. Set the repository's CI isolation flag.
5. Run `python -m unittest discover -s tests -v`.

The suite is discovered dynamically. The workflow will not hard-code the
current count of 93 tests, so newly added tests are included without a workflow
change.

## Bubblewrap Enforcement

Local runs retain the existing fail-closed behavior: destructive isolation
tests cannot affect the host, and the positive capability test may skip when
Bubblewrap cannot operate in an already restricted environment.

CI sets `PYPTO_SKILLS_REQUIRE_BWRAP=1`. When that flag is present, the positive
capability test must fail instead of skipping if `validation-sandbox.sh` cannot
start a sandbox and execute its probe. This verifies the production helper
rather than only checking that a `bwrap` executable is installed.

The existing negative tests continue to verify that validation:

- sees only the prepared commit snapshot;
- cannot push with Git;
- cannot perform a GitHub CLI write;
- cannot read host tokens, SSH state, or home-directory credentials; and
- cannot write outside the temporary snapshot.

## Tool Configuration

Add `requirements-ci.txt` with `ruff==0.16.0` and `pyright==1.1.410`. Add
explicit Ruff and Pyright configuration to `pyproject.toml`, targeting Python
3.10, so future dependency upgrades cannot silently change either the
supported language level or the selected checks.

CI dependency updates will be intentional repository changes. No runtime
dependency is added to the skills bundle: the tools are needed only to validate
the repository.

## Failure Behavior

Any failing unit test, Bubblewrap capability failure, lint diagnostic, format
difference, type error, or shell syntax error fails its job. Jobs do not use
`continue-on-error`, and the Python matrix does not use `fail-fast`, allowing
both interpreter results to remain visible when one fails.

## Acceptance Criteria

- A pull request starts both workflow jobs.
- The unit suite passes on Python 3.10 and Python 3.14 with no Bubblewrap
  capability skip.
- The quality job passes with pinned Ruff and Pyright versions and validates
  every tracked shell script.
- Deliberately making the Bubblewrap probe unavailable causes the tests job to
  fail.
- The workflow token has read-only repository permissions and checkout leaves
  no persisted credential for tests.
